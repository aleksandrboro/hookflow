# Техническое задание: HookFlow

**Версия:** 0.1 — учебный MVP  
**Тип приложения:** сервис планирования и повторной доставки webhook’ов  

## 1. Краткое описание

HookFlow принимает от клиента задачу отправить HTTP POST-запрос на заданный URL сейчас или в указанное время. Сервис сохраняет задачу в PostgreSQL, а отдельный worker отправляет webhook. Результат и каждая попытка доставки сохраняются. При временной ошибке worker повторяет отправку по заданной политике.

Главный принцип: **PostgreSQL — источник истины для задач и их состояния, Redis Streams — очередь доставки готовых задач worker’ам.** Redis также применяется для rate limiting. Событие в Redis можно восстановить из PostgreSQL; потеря Redis не должна приводить к потере принятой задачи.

## 2. Цели MVP

1. Создать задачу доставки webhook’а.
2. Запланировать отправку на будущее либо отправить как можно скорее.
3. Передавать готовые к отправке задачи worker’ам через Redis Streams consumer group.
4. Посмотреть статус задачи и историю попыток.
5. Отменить ещё не начатую задачу.
6. Повторить доставку после временной ошибки.
7. Сохранить задачи при перезапуске API, Redis или worker’а; недоставленные события восстанавливать из PostgreSQL/outbox.
8. Ограничивать частоту создания задач через Redis.
9. Запускать окружение локально через Docker Compose.
10. Продемонстрировать API и worker в локальном Kubernetes.

## 3. Не входит в первую версию

- веб-интерфейс;
- пользовательские аккаунты, биллинг и сложное управление tenant’ами;
- recurring/cron-задачи;
- приоритетные очереди;
- гарантированная доставка «ровно один раз»;
- произвольное исполнение shell-команд;
- собственный кластер PostgreSQL или Redis для production;
- отдельный брокер сообщений вроде Kafka или RabbitMQ; для очереди доставки в MVP используются Redis Streams и PostgreSQL outbox.

## 4. Пользовательский сценарий

1. Клиент авторизуется API-ключом.
2. Отправляет запрос на создание задачи с URL-получателем и JSON payload.
3. HookFlow валидирует запрос и сохраняет задачу.
4. API возвращает `202 Accepted` и ID задачи.
5. Worker забирает наступившую по времени задачу и отправляет HTTP POST.
6. Worker сохраняет ответ или ошибку.
7. Клиент запрашивает статус и историю попыток.

### Пример использования

Предполагается, что локально запущен `mock-receiver` с маршрутом `/fail-once`: он возвращает `500` при первой доставке и `200` при следующей. Это позволяет проверить retry без внешнего сервиса.

```bash
curl -i -X POST http://localhost:8080/v1/jobs \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: dev-key' \
  -H 'Idempotency-Key: invoice-1042-paid' \
  -d '{
    "url": "http://mock-receiver:8090/fail-once",
    "payload": {
      "event": "invoice.paid",
      "invoice_id": "inv-1042"
    },
    "max_attempts": 4
  }'
```

Если `run_at` не передан, задача готова к выполнению сразу после создания. Для отложенного запуска передаётся время в формате RFC 3339 UTC, например `"run_at": "2030-01-01T12:00:00Z"`.

Пример ответа:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json
```

```json
{
  "id": "b16f91c8-8d17-4f1e-8bc4-0ae34ca3a0ae",
  "status": "pending",
  "created_at": "2026-10-13T09:00:00Z",
  "run_at": "2026-10-13T09:00:00Z"
}
```

Проверка статуса:

```bash
curl -i http://localhost:8080/v1/jobs/b16f91c8-8d17-4f1e-8bc4-0ae34ca3a0ae \
  -H 'X-API-Key: dev-key'
```

Проверка попыток доставки:

```bash
curl -i http://localhost:8080/v1/jobs/b16f91c8-8d17-4f1e-8bc4-0ae34ca3a0ae/attempts \
  -H 'X-API-Key: dev-key'
```

После первой ошибки задача может иметь статус `retrying`; после успешной повторной доставки — `succeeded`.

## 5. Интерфейс API

Все запросы и ответы используют JSON. Для MVP используется API-ключ из конфигурации приложения. В будущем ключ может сопоставляться с отдельным tenant.

### `POST /v1/jobs`

Создаёт задачу.

**Заголовки:**

- `X-API-Key: ...` — обязателен;
- `Idempotency-Key: ...` — обязателен для MVP, уникален в пределах клиента;
- `Content-Type: application/json`.

**Тело запроса:**

| Поле | Тип | Обязательное | Правило |
|---|---|---:|---|
| `url` | string | да | Только `http` или `https`; должен пройти проверку безопасности |
| `payload` | object | да | Валидный JSON, не больше 64 KiB |
| `run_at` | RFC 3339 string | нет | Если отсутствует — запускать как можно скорее |
| `max_attempts` | integer | нет | По умолчанию 5, допустимый диапазон 1–10 |

**Успешный ответ:** `202 Accepted`, ресурс задачи с ID и начальным статусом.

**Идемпотентность:** повтор с тем же ключом и тем же телом возвращает существующую задачу. Повтор с тем же ключом, но другим телом возвращает `409 Conflict`.

### `GET /v1/jobs/{job_id}`

Возвращает задачу, её статус, времена создания и следующего запуска, число попыток и последнюю ошибку, если она есть.

### `GET /v1/jobs/{job_id}/attempts`

Возвращает историю попыток: номер, начало и конец, HTTP status, длительность и краткое описание ошибки. Полное тело ответа получателя не сохраняется.

### `POST /v1/jobs/{job_id}/cancel`

Отменяет задачу в статусе `pending`, `retrying` или `queued`. Если для `queued` задачи сообщение уже находится в Redis Stream, worker при чтении увидит `cancelled`, не отправит webhook и подтвердит сообщение. Для уже выполняемой или терминальной задачи возвращает `409 Conflict`.

### Коды ошибок

- `400 Bad Request` — некорректный JSON или параметры;
- `401 Unauthorized` — отсутствует или неверный API-ключ;
- `404 Not Found` — задача не найдена;
- `409 Conflict` — конфликт idempotency key или недопустимая операция со статусом;
- `413 Payload Too Large` — payload превышает лимит;
- `429 Too Many Requests` — превышен лимит создания задач;
- `503 Service Unavailable` — проверка rate limit недоступна.

## 6. Статусы и правила выполнения

Основные статусы:

- `pending` — ожидает времени первого запуска;
- `queued` — наступило время запуска, задача передана через outbox/Redis Stream и ждёт захвата worker’ом;
- `running` — захвачена worker’ом;
- `retrying` — временная ошибка, ожидает следующей попытки;
- `succeeded` — получен успешный HTTP-ответ;
- `failed` — постоянная ошибка, для которой retry не выполняется;
- `dead` — временные ошибки повторялись до лимита попыток;
- `cancelled` — отменена до начала выполнения.

### Политика ответа получателя

- любой `2xx` — успешная доставка;
- timeout, сетевой сбой, `408`, `429` и `5xx` — временная ошибка, допускающая retry;
- другие `4xx` и `3xx` — постоянная ошибка в MVP;
- редиректы автоматически не выполняются, чтобы не обходить проверку URL.

Число попыток включает первую отправку. Задержка между повторными попытками увеличивается экспоненциально и ограничивается сверху; к ней добавляется jitter. Базовая формула: `min(base_delay * 2^(attempt-1), max_delay) + jitter`.

### Гарантии доставки

Сервис предоставляет доставку **как минимум один раз**, а не «ровно один раз». После сетевого сбоя возможно, что получатель обработал запрос, но worker не успел записать результат. Повторная отправка должна быть безопасной для получателя.

Каждая отправка включает стабильный идентификатор, например `X-Delivery-ID: <job_id>`, и номер попытки `X-Delivery-Attempt`. Получатель может использовать `X-Delivery-ID` для дедупликации.

## 7. Архитектура

```text
Клиент ──> Go API ──> PostgreSQL (jobs + outbox)
              │                    │
              │                    └── Outbox relay ──> Redis Stream
              │                                             │
              └── rate limit ──> Redis                     ▼
                                            Worker consumer group
                                                     │
                                                     └── HTTP POST ──> Receiver
```

PostgreSQL хранит авторитетное состояние и надёжный outbox. Redis Streams доставляет события worker’ам, но не заменяет запись задачи в PostgreSQL.

### API

- проверяет API-ключ и входные данные;
- применяет rate limit;
- создаёт или возвращает существующую idempotent-задачу;
- предоставляет чтение статуса, попыток и отмену.

### Scheduler и outbox relay

- Scheduler выбирает из PostgreSQL задачи `pending` или `retrying`, для которых наступил `available_at`.
- В одной транзакции он переводит задачу в `queued` и добавляет событие `delivery.ready` в таблицу outbox.
- Outbox relay публикует неопубликованные события в Redis Stream `hookflow:deliveries` командой `XADD`, после чего отмечает событие опубликованным в PostgreSQL.
- Если relay упадёт после `XADD`, но до отметки в БД, событие может попасть в Stream повторно. Это допустимо: worker проверяет состояние job в PostgreSQL и не начинает уже завершённую задачу.
- Reconciler периодически проверяет `queued`-задачи, застрявшие без обработки, и `running`-задачи с истёкшим `locked_until`; он повторно ставит их на обработку через outbox. Это позволяет восстановить доставку, если Redis перезапустился и потерял сообщение, либо worker погиб.

Scheduler, outbox relay и worker можно сначала собрать в одном Go-процессе для простоты, но оставить раздельными компонентами в коде. Позже worker можно запускать отдельным Kubernetes Deployment.

### Worker

- читает Redis Stream через consumer group `hookflow-workers` с помощью `XREADGROUP`;
- в короткой транзакции проверяет состояние задачи и переводит `queued` в `running`;
- фиксирует lease (`locked_until`) и завершает транзакцию **до** HTTP-запроса;
- отправляет webhook с ограниченным timeout;
- сохраняет попытку и новое состояние в PostgreSQL;
- подтверждает сообщение командой `XACK` только после сохранения результата;
- возвращает зависшие pending-сообщения в обработку через механизм восстановления consumer group, например `XAUTOCLAIM`.

При retry worker переводит задачу в `retrying`, задаёт новое `available_at` и подтверждает старое сообщение. Когда наступит время повторной попытки, Scheduler снова создаст outbox-событие и отправит его в Stream.

При сбое worker’а после фактической отправки webhook, но до записи результата, получатель может получить повторный запрос. Поэтому сохраняются стабильный `X-Delivery-ID` и требование к идемпотентной обработке на стороне получателя.

### Redis — обязательная часть проекта

Redis используется в двух конкретных сценариях:

1. **Redis Streams** — очередь готовых доставок для worker’ов. Используются Stream `hookflow:deliveries`, consumer group `hookflow-workers`, pending entries, подтверждение после обработки и восстановление зависших сообщений.
2. **Rate limiting** — атомарное ограничение числа запросов `POST /v1/jobs` на API-ключ. Состояние лимитера временное и хранится в Redis с TTL.

PostgreSQL остаётся источником истины: в нём хранятся jobs и outbox. Redis Streams — канал передачи работы, а не единственная копия расписания. При недоступности Redis relay оставляет outbox-события неопубликованными и повторяет публикацию после восстановления. Новые `POST /v1/jobs` получают `503`, если rate limit нельзя проверить; ранее сохранённые задачи не теряются. Повторные события из Stream безопасны благодаря проверке состояния job в PostgreSQL.

## 8. Данные PostgreSQL

### Таблица `jobs`

Минимальные поля:

- `id UUID PRIMARY KEY`;
- `tenant_id` или идентификатор API-ключа;
- `target_url`;
- `payload JSONB`;
- `status`;
- `run_at`, `available_at`;
- `attempt_count`, `max_attempts`;
- `idempotency_key`;
- `worker_id`, `locked_until`;
- `last_http_status`, `last_error`;
- `created_at`, `updated_at`, `finished_at`.

### Таблица `delivery_attempts`

Минимальные поля:

- `id UUID PRIMARY KEY`;
- `job_id` — внешний ключ на задачу;
- `attempt_no`;
- `started_at`, `finished_at`;
- `http_status`;
- `duration_ms`;
- `outcome`, `error_message` (ограниченной длины).

### Таблица `outbox_events`

Outbox хранит события, которые нужно опубликовать в Redis Stream:

- `id UUID PRIMARY KEY` — идентификатор события;
- `job_id` — ссылка на задачу;
- `event_type` — для MVP `delivery.ready`;
- `created_at`;
- `published_at` — `NULL`, пока событие не опубликовано;
- `publish_attempts`, `last_error`.

Создание outbox-записи и перевод job в `queued` выполняются **в одной транзакции PostgreSQL**. Relay публикует событие в Redis и затем фиксирует `published_at`. Если процесс падает в промежутке между публикацией и фиксацией, возможен дубль; обработчик обязан быть идемпотентным.

### Индексы и ограничения

- уникальность `(tenant_id, idempotency_key)`;
- индекс для выбора готовых задач по времени `available_at` и статусу;
- индекс неопубликованных outbox-событий по `created_at` с условием `published_at IS NULL`;
- индекс попыток по `job_id`;
- внешние ключи и проверки допустимых значений там, где это уместно.

## 9. Безопасность

- Для MVP API защищён ключом `X-API-Key`; секрет хранится в переменной окружения, не в Git.
- Максимальный размер payload — 64 KiB.
- URL допускает только `http` и `https`.
- В MVP для локальной демонстрации рекомендуется allowlist разрешённых host’ов, включая `mock-receiver`.
- Для более общего использования блокировать loopback, private, link-local и metadata IP-адреса; не следовать редиректам без повторной проверки адреса назначения.
- Не сохранять полные тела ответов получателей и не писать payload в логи по умолчанию.
- HMAC-подпись исходящих webhook’ов — хорошее расширение после MVP.

## 10. Docker и Kubernetes

### Docker Compose

Локальный `compose.yaml` поднимает:

- `api`;
- `worker`;
- `postgres`;
- `redis`;
- `mock-receiver`.

Ожидаемая команда запуска: `docker compose up --build`. Миграции запускаются отдельной документированной командой или миграционным контейнером.

### Kubernetes

В `deploy/k8s/` разместить:

- Deployment для API;
- Service для API;
- отдельный Deployment для worker;
- ConfigMap и Secret;
- readiness/liveness probes;
- resource requests/limits.

Для локальной демонстрации зависимости можно поднять через готовые charts или подключить отдельно. Эксплуатация PostgreSQL в production-кластере не является целью MVP.

## 11. Нефункциональные требования

- После успешного `202 Accepted` задача уже сохранена в PostgreSQL.
- Перезапуск API не удаляет задачи.
- Worker использует ограниченную параллельность; значение конфигурируется, начальное значение — 10.
- HTTP timeout доставки по умолчанию — 5 секунд.
- Scheduler и outbox relay проверяют PostgreSQL с настраиваемым интервалом, по умолчанию — 1 секунда; чтение Redis Stream выполняется блокирующим ожиданием с коротким timeout.
- Worker корректно завершает работу по сигналу остановки и не начинает новые задачи после начала shutdown.
- Логи содержат `job_id` и `attempt_no`, но не секреты и payload по умолчанию.
- Результаты нагрузки описываются вместе с условиями тестирования; не заявлять production-grade пропускную способность на основании локального ноутбука.

## 12. Проверки и критерии приёмки

1. Валидный `POST /v1/jobs` возвращает `202` и ID задачи.
2. Задача появляется в PostgreSQL и остаётся там после перезапуска API.
3. Задача с будущим `run_at` не доставляется до указанного времени.
4. Успешный ответ mock receiver переводит задачу в `succeeded`.
5. `500` или timeout создаёт попытку и планирует retry.
6. После достижения `max_attempts` задача получает статус `dead`.
7. Постоянный `4xx` переводит задачу в `failed` согласно описанной политике.
8. Повторный запрос с тем же idempotency key не создаёт вторую задачу.
9. Отмена задачи в `pending`, `retrying` или `queued` предотвращает отправку webhook’а; уже опубликованное сообщение Redis при обработке подтверждается без отправки.
10. Несколько worker’ов не захватывают одну `queued`-задачу одновременно в обычном сценарии.
11. История попыток доступна через API.
12. Остановка worker’а во время задачи не оставляет её навсегда в `running`; после истечения lease она снова доступна для обработки.
13. Redis Streams consumer group принимает несколько задач и распределяет сообщения между worker’ами.
14. Сообщение подтверждается через `XACK` только после сохранения результата обработки в PostgreSQL.
15. При сбое outbox relay между `XADD` и фиксацией `published_at` дубль не приводит к повторному захвату уже завершённой job.
16. При перезапуске Redis задачи не теряются: неопубликованные outbox-события публикуются после восстановления, а застрявшие `queued` jobs подхватывает reconciler.
17. Отключение Redis не стирает расписание; после восстановления Stream обработка продолжается.
18. Запрещённый адрес получателя отклоняется до постановки задачи или до отправки.
19. `docker compose up --build` поднимает тестовый стек; unit- и integration-тесты проходят.
